# Writing a useful game design document

Researched: 2026-09-27
Scope: personal reference for solo and small-team games. The proposed structure is engine-independent; no game has been designed or playtested with it yet.

## What a GDD should accomplish

A useful GDD explains what players do, why those choices matter, how the game responds, and what the team is choosing to build. It gives future you enough context to understand a rule without replaying the conversation that produced it. It should expose uncertain design assumptions rather than make them look settled.

Unity's GDD tutorial treats the document as an organizing tool for both individuals and teams, permits different formats, and connects feature priorities with player feedback. Our inference is to keep a common set of design questions while scaling detail to the project. The tutorial is labeled Unity 2022.3, but these documentation principles do not depend on that Editor version.

## Start small, then deepen the risky parts

Start with a short overview, a few experience pillars, a concrete core loop, scope limits, and the next experiment. Describe a representative moment of play before listing many features. For example, “the player chooses whether to spend their last light source to explore an optional room” communicates a decision more clearly than “exploration system.” This is an illustrative example, not a proposed game requirement.

A one-page design can communicate a focused idea quickly. It need not contain the entire game: use a short overview and expand the rules that require detail.

Our template uses a concept-first pass, followed by independent sections for mechanics, progression/content, controls/accessibility, presentation, and production constraints. Add substantial detail where another person would otherwise have to guess the behavior. Split large subsystems into focused documents when necessary, retaining a meaningful summary of their player-facing contract in the GDD.

## Separate vision, rules, and evidence

“Movement feels forgiving” is an experience goal. “A buffered jump is consumed once on landing within the configured window” is an observable rule. A playtest observation explains whether the behavior supports the intended experience. Keep all three distinct.

Label ideas proposed, decisions chosen, and observations tested. A decision is not proof of implementation; a successful automated test is not proof of player enjoyment. Record important changed decisions with dates and reasons, while updating the current rule where readers expect it.

Our recommendation is to keep detailed class design and task tracking outside the GDD. Include technical constraints only when they affect the design: target device, input, loading expectations, persistence, or performance requirements. Use a feature specification for implementation-level requirements and scenarios once a system warrants one, without making the GDD dependent on that document to explain the experience.

## Scope is a design decision

Unity and USC's design-process unit explicitly connects scope and constraints to completing a game. Our template therefore asks what the smallest prototype must prove, what a representative production slice would demonstrate, and what release essentials exclude. These are different questions, not three mandatory project phases.

For a small team, record content ranges and uncertainties rather than inventing precise level counts or dates. A feature belongs in scope because it supports the intended experience within the team's capacity, not because another game includes it.

## Include accessibility while rules are still changeable

Microsoft's Xbox Accessibility Guidelines organize design guidance around player impact, scoping questions, and implementation considerations. They are design and testing resources, not a claim of legal compliance. Our GDD prompts cover relevant input, sensory, cognitive, timing, and motion barriers, alongside planned player feedback. They do not assert that every project needs every possible option.

## 2026-09-27: Template decision and use

The reusable file is `agent-docs/template/game-design-document.md`. Copy it into the canonical game's notes or its established documentation location, then replace prompts with actual decisions or marked unknowns. It includes its own instructions and contents; using it requires no external download or reading this research note.

The format is an original synthesis of the sources and our note conventions, not a copied studio template or universal industry standard. Keep sections concise, remove unused example rows, and use “not applicable” with a reason where a mechanic or mode does not exist. No implementation gotchas are generated by this research.
