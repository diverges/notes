Status: Source/capture review retained; original layout proposal rejected. Current direction is style refinement of the existing game UI.
Updated: 2026-10-01.
Scope: Player-facing game interface. This is the historical review; implementation was subsequently authorized on 2026-10-01 and documented in ui-conversion.md. Earlier no-code restrictions below are superseded.

Tighten whitespace first: trial general panel padding 16 to 12 logical pixels and header gap 16 to 8; preserve existing compact Bag/Equipment overrides and current slot/input target sizes. Adjust font metrics before shrinking rows. These are comparison values, not approved implementation instructions. Keep the current log placement and panel layout.

## 1: Overview and evidence

The current interface has a useful sparse structure and already uses the approved palette. Its largest weaknesses are decision information, prototype-facing language, and inconsistent presentation. Correct misleading combat descriptions and expose action states before adding decorative assets.

Reviewed the current BootstrapHud partials, WorldActionGui, StartScreen, their styles and panel settings, player/enemy/action data, combat feedback, item icon GUIDs and project audio files. Visually inspected ten existing gameplay captures: title-forest-wide, world-crafting-smoke, combat-v2-engaged, combat-v2-enemy-warning, inventory-hover-layout, equipment-panel, crafting-empty, crafting-complete, ui-palette-skills and ui-review-settings.

These captures span multiple revisions. The older Settings capture incorrectly says all panels pause; the current source says Bag, Equipment and Skills remain live. Older Skills captures predate active combat skills. Their 100 HP displays and prototype environments are historical. Current combat begins at 20 HP and supports fractions. Current source takes precedence for behavior; screenshots establish only the appearance of their captured revision. Some current UI states lack current captures.

Computer Use was not approved to access the Unity-hosted game window. No live game inspection, input test, audio audition or browser build was performed. This is a completed design review with explicit validation limits, not a claim that usability or artistic quality has passed playtesting.

## 2: Experience and design pillars

| Pillar | Proposed interface rule | Evaluation |
| --- | --- | --- |
| An exposed wanderer in an eerie forest | Preserve the center and the navigable ground; use restrained peripheral panels. | Player can see nearby threats while choosing inventory actions. |
| Slow work with understandable consequences | Explain the action, reason it cannot proceed, and where its result went. | Player can distinguish working, blocked, cancelled and completed. |
| Discovery without interface guesswork | Keep recipes hidden; explain slot order, selection and eligibility. | Player understands how to experiment without being given recipes. |
| Worn, practical belongings | Charcoal surfaces, bone text, worn brass rules and simple etched silhouettes. | UI feels related to the weathered title and low-detail world without hiding text. |
| Quiet routine, clear danger | Small material sounds for input; stronger but restrained threat feedback. | Repeated gathering remains comfortable; warnings survive muted sound. |

Proposed direction: material restraint rather than ornate fantasy frames. Heavy parchment would introduce a large bright surface in a dark forest; dense decorative borders would consume space and compete with small items. Keep current rectangular geometry, using subtle irregularity only at edges.

Representative journey: notice a loose stick → see “Pick up Stick” → click and see approach/arrival → receive one compact result → inspect the six-slot bag → select materials → learn crafting order without a recipe list → inspect a matched result and its requirements → see work/consumption/output → inspect the new tool's effects → encounter danger → move away or recover clearly after defeat.

Fire inspection is a follow-up candidate: FireInstance tracks lit/off state and remaining time, but reviewed HUD has no dedicated fuel readout. Prefer state and remaining burn time on inspection, not another persistent survival meter. Do not infer warmth, hunger, stamina or poison systems from the theme.

## 4: Interface behavior

### HUD and combat

Preserve top-left health, lower-right Bag/Equipment/Skills/Settings, one open panel, no minimap and no combat cast bar. Proposed health reads current/max with a proportional bar; use a consistent fractional display policy so tiny damage does not disappear behind integer rounding. A compact integer HUD with exact values on inspection is possible, but the policy needs agreement.

Show target information only while selected/engaged, not above every creature. The health bar communicates remaining health; do not attach an overall combat-level or easy/hard rating until its definition and tuning are validated. Damage and BLOCK remain brief world feedback. Acid telegraphs need a distinct shape/pattern for falling versus active ground; do not use color alone.

Keep UI crisp over the retro-rendered world. Avoid world dithering on body text or thin glyphs. Short opening transitions should not delay input. Reduced motion/flash should suppress pulses and combat blinking while preserving static state and warnings.

### Inventory and equipment

Keep six visible slots, quantities, selected and reserved states, drag-to-swap and click alternatives. Add “2 / 6 slots” and a readable explanation of reservations when inspected. Reserved quantities need a mark as well as color. Show item name and primary action on hover/focus, with right-click instructions where needed.

The established first action varies: ordinary stack selects Use, gear equips, a station drops into the world, and some materials trigger a recipe. Label the actual action; “Use” cannot stand in for every behavior. During equipment comparison show what happens to the old item, including a bag-space failure. Keep dangerous Drop visually distinct without a confirmation dialog for every routine reversible action.

### Crafting and skills

Preserve centered three ordered ingredient slots, matched output and embedded six-slot bag. Number slots subtly and teach “Order matters.” Empty and invalid combinations remain quiet; do not play failure sounds on every tentative arrangement. A ready result shows its name, count, time and eligible costs before Craft. A blocked matched result shows its concrete requirement beside the button. Reserved materials and interruption outcome must be understandable.

Skills detail should state: Vitality increases maximum health and currently gains XP on damaging incoming hits; Weapon Proficiency affects hit chance against Block and gains XP on landed attacks; Strength increases raw damage; Block affects avoidance and mitigation. Strength/Block training policy remains pending. Woodcutting and Survival should explain their implemented activities without listing secret recipes.

### Log, settings, title and recovery

The log remains the place to revisit Examine and results, but should not be the sole place for urgent failures, defeat or selected-item mode. Coalesce identical routine gains without losing totals. Prototype debug/error text should be distinguished from player-facing explanations.

Settings remains paused. Proposed groups: audio, display/readability, input help/camera and prototype tools. Keep the existing title artwork; style Start with the same type and focus language as the game. Production saves and recovery cannot be represented as functioning until implemented. For this prototype, make Reset test discoverable after defeat without presenting it as canonical resurrection lore.

## 5: Progression and content

Six active skill definitions were inspected: Woodcutting, Survival, Vitality, Weapon Proficiency, Strength and Block. Woodcutting and Survival have assigned PNG icons; the four combat skills have null icon fields and fall back to a diamond. Cooking, Smithing and Agility are hardcoded deferred rows, not additional implemented skill activities.

All 23 item definitions under Assets/Data/Items have icon GUIDs resolving to existing PNG metadata. That verifies coverage, not small-size quality. Reconcile silhouettes and naming for Wooden shield versus Wood Shield and Woodcutting axe versus Stone Axe, preserving genuine gameplay distinctions. Item icon replacement is a consistency task; it is not a missing-icon backlog for all items.

Avoid adding new progression, quests, maps, crafting discovery books or survival meters as part of a UI reskin. Those require separate game design.

## 6: Controls, interface, and accessibility

Proposed component baseline at 1280×800 reference size: body 16 logical pixels, secondary text at least 14, headings 22–26, targets at least 40×40. These are starting values for testing, not measured accessibility compliance. Use one body face, with a restrained serif for short headings. Test I/l/1, O/0, decimal damage, ×, arrows and needed language glyphs before selection.

Common states: normal, hover, keyboard focus, pressed, selected, disabled-with-reason. Give focus a distinct edge and selected a persistent notch/underline. Use text plus shape for danger and failure. Do not lower disabled explanatory text until unreadable.

Preserve click alternatives to dragging. Inventory/equipment already implement some keyboard activation; this does not prove end-to-end keyboard access. World actions use pointer handling and require a dedicated keyboard interaction pass if that support is chosen. Touch/controller are unverified future targets, not claimed support.

Test game UI at 1280×720, 1280×800, 1920×1080, narrow browser aspect and increased text scale. Check contextual menu clamping, live panel height, crafting fit, tooltip overlap, quantity readability and action cues at night. Contrast must be measured for final colors over actual backgrounds, particularly secondary text and thin borders.

### UI sound register

Existing first-pass project clips include Equip, Unequip, Pickup, LevelUp, Experience, CraftWork, StoneWork, fire cues, footsteps and combat Swing/Engage/Block/hit sounds. Player interaction feedback has assigned cue references; current HUD/Start/world-menu code has no explicit menu sound calls. Thus gameplay confirmation has a foundation, while a dedicated menu sound layer is missing in the reviewed implementation. Installed plugin demo sounds are not evidence of shipped UI integration.

No clips were auditioned. “Retain/review” means existing candidate, not an endorsement of sound quality or mix.

| Event | Status | Proposed sound and trigger | Visual partner |
| --- | --- | --- | --- |
| Panel open / close | Missing dedicated HUD hook | Soft cloth pull and shorter release, 120–220 ms; share across panels, vary subtly. | Panel and selected navigation state |
| Focus / hover | Missing dedicated hook; optional | Very quiet dry tick, 30–60 ms. Rate-limit; silence rapid pointer travel or disable entirely. | Focus edge |
| Confirm / Start / menu choice | Missing dedicated hook | Dry wood/brass tap, 60–120 ms, on accepted input once. Avoid an additional layer if the successful action already has a cue. | Accepted state or transition |
| Back / cancel Use | Missing dedicated hook | Softer falling tap, 60–120 ms. Fire once when a layer actually closes. | Selection cleared |
| Bag reorder / ingredient placement | Missing dedicated hook | Small cloth/wood placement, 60–120 ms, on accepted drop/click. No sound each drag frame. | Slot move and reserved marker |
| Rejected action / full bag | Missing dedicated menu hook | Low dull knock, 100–180 ms, once per attempted action. Never alarm while merely exploring invalid combinations. | Local reason text |
| Pickup / equip / unequip | Existing clips and gameplay cue wiring | Audition and retune existing cues first. Avoid duplicate confirm sounds. | Quantity/item change |
| Craft work / XP / level-up | Existing candidates | Keep work subdued; review frequent XP chime for fatigue. A rare warmer level-up tail may last 400–800 ms. | Output and skill gain |
| Low health | No dedicated warning found in reviewed HUD | Optional subdued pulse on entering danger, with cooldown and disable control; do not loop over every hit. Threshold remains proposed. | Persistent health warning |

| Enemy engagement / attack / block / hit | Existing gameplay cues | Audition separation from menu cues. Preserve positional world information. | Target state, telegraphs and outcome text |

Produce new short UI effects as clean WAV masters with trimmed starts, short fades and no clipping. Keep master/source files and variation sets. Menu sounds should be non-spatial; world contact and creature cues remain spatial where appropriate. Define Master/UI/World/Music controls before mix approval. UI cues must remain usable in Settings while gameplay is paused. Rate-limit overlapping messages and let important danger cues remain audible over routine input. Final loudness requires listening in the game; no loudness or mix measurement is claimed.

## 8: Scope and verification

### Recommended sequence

1. Information pass: stale sword copy, defeat/recovery, selected action, crafting reasons, equipment effects and skill explanations.
2. Coherent UI kit: font trial, four missing skill icons, shared focus/selection, navigation and item consistency.
3. Audio pass: audition existing interactions, create missing menu family, add controls and tune repetition.
4. Player review in the actual game: day/night, combat, overflow, crafting failures, pause/focus and narrow windows.

No implementation is authorized by this review. Production font choice, polished asset creation and sound production are later work after direction feedback.

### Review checks completed

Read current game UI and data, inspected ten saved player-facing captures, resolved all 23 item icon GUIDs to PNG metadata, identified four null skill icons, checked project font presence and menu sound call sites, and compared sword copy with current attack profiles. Created and visually inspected a vector design board. No game tests were run because no game files were changed.

### Acceptance scenarios for later playtesting

| Scenario | Evidence to seek |
| --- | --- |
| First-time player gathers and uses an item | Can name default action, find more actions and cancel Use without coaching. |
| Valid / invalid / blocked craft | Can explain slot order, distinguish no combination from unmet requirements, and identify resulting cost/output without a recipe list. |
| Equipment choice | Can compare the two swords without being misled by fixed damage copy. |
| Skill progression | Can explain the four combat roles and identify which currently lack an XP earning rule. |
| Combat and queen acid at night | Can identify engaged target, health danger and safe ground with sound muted. |
| Bag full / ground overflow | Can tell whether an item was lost, left or collected and recover the remaining drop. |
| Settings / focus loss / return | Correctly knows when simulation is paused and when danger continues. |
| Defeat | Can find recovery without searching log history; production consequences remain explicit unknowns. |
| Long gathering session | Repeated input/XP sounds do not fatigue or mask the environment. |
| Small window / large text | No clipped actions, unreadable counts, offscreen controls or overlapping critical warnings. |

Human aesthetic and usability acceptance remains pending. This review provides testable hypotheses, not proof of immersion.

## 9: Decisions and open questions

Confirmed constraints retained: player-facing game UI only; no code changes; gloomy PSX forest direction; palette; six-slot Bag; four navigation buttons; hidden ordered crafting; no minimap; live non-Settings panels; no combat cast bar.

Proposed, not decided: serif headings, current/max health, target health panel, collapsible recent log, contextual intention text, matched-craft reasons, gear comparisons, new menu cues and reduced-flash options.

Open decisions: production defeat and persistence rules; supported window/input/language targets; exact font family and rights; whether target health is numeric or bar-only; how to display fractional health; Strength/Block training; whether XP chimes survive repetition testing; optional fire burn-time inspection. These do not block a design proposal but do block final implementation/asset acceptance.
